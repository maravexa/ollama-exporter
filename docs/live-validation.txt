Accounting/fidelity evidence
For every case, request body SHA256 at the relay matched the client request body,
including the usage options; the exporter did not inject options. Response entity
body SHA256/length at the real Ollama connection matched what the client received.
Status and observed non-framing end-to-end headers matched. The observer relay
re-chunks HTTP transfer framing, so it deliberately excludes Content-Length,
Transfer-Encoding and Connection from header comparison. No trailers were
advertised by the live server; trailer forwarding remains covered by HTTP fixtures.
This is body-byte fidelity, not a claim about identical TCP/chunk boundaries.

Each completed request produced exactly one requests_total increment, exactly one
request-duration observation, and returned in-flight to zero. Every native case
produced one native eval and prompt-duration observation. Compatibility requests
produced no native eval/prompt/load histogram deltas and left native TPS unchanged.
Each of the four usage-absent streams produced skipped/usage_absent exactly once,
counted the completion, and added NO token histogram observations (not zeros).
The six compatibility responses with usage each observed input/output counts once.

First-content delivery evidence
All 9 streaming cases in the 14-case matrix passed a synchronized live-body gate:
the observer relay paused after sending the first content-bearing portion of an
actual Ollama stream, and the client received first content before acknowledging
and releasing the relay. The exporter therefore forwarded content while relay EOF
was blocked. The relay can change buffering and adds audit overhead, so these
measurements are not an estimate of pure proxy overhead or backend token latency.

The separate 5-case run configured the exporter DIRECTLY against :11434, with no
relay, gate or simulated upstream. Measured first content / response completion:
  /api/generate: 0.102 s / 1.244 s
  /api/chat: 0.097 s / 1.236 s
  /v1/chat/completions: 0.098 s / 1.236 s
  /v1/completions: 0.102 s / 1.239 s
  /v1/messages: 0.097 s / 1.237 s
Each direct stream had a terminal event and exactly-once duration/completion
accounting, with in-flight returning to zero. Thus the direct first-content range
was 0.097-0.102 s, versus 1.236-1.244 s completion for these short warmed requests.
These are observed samples, not a latency guarantee.
